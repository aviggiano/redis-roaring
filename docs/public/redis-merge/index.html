Who am I · CONCISE

Some background: CONCISE by hand (circa 2015)

  • CONCISE: Compressed 'n' Composable Integer Set (Colantonio & Di Pietro, 2010), from the WAH family of word-aligned RLE bitmaps.
  • Literal words carry 31 raw bits; fill words run-length encode stretches of 0s/1s, plus 5 "position" bits that fold one stray bit into a fill, halving WAH's worst case.
  • Implemented in C from the paper: mod-31 boundary arithmetic, fill merging, literal→fill promotion. Every AND/OR/NOT is a word-by-word merge of two compressed streams.

✅ What it did well

Excellent compression for sparse and clustered data; set algebra without decompressing.

⚠️ The limitation

No random access: reading bit N means scanning from the start. Operations are branchy, sequential, and cache-unfriendly, and they degrade as the data grows.

Who am I · redis-roaring

Some background: Porting to CRoaring (circa 2016)

  • Ported the engine from CONCISE to Roaring bitmaps: chunked containers instead of one compressed stream. The founding paper reports intersections up to 900× faster than WAH/CONCISE-style RLE bitmaps.
  • Random access plus vectorized kernels: large gains on exactly the queries that were slow.
  • May 2017: published redis-roaring, a Redis module wrapping CRoaring behind Redis-style commands (R.SETBIT, R.BITCOUNT, …).
  • 385 ★ · in production use · benchmarked on real census data on every push: parity on O(1) ops, up to 8× faster on O(N) ops.

💡 Why go native

A module proves the value but lives outside the type system: separate commands (R.*), separate keys, its own persistence callbacks. Making the existing bitmap API compressed removes all of that: no new API, and existing workloads get cheaper.

The problem

What bitmaps are used for, and why Redis needs compressed bitmaps.

The problem

Redis bitmaps today: commands over a string

  • There is no bitmap type: a bitmap is a string, addressed bit by bit.
  • Seven command families: SETBIT · GETBIT · BITCOUNT · BITPOS · BITOP · BITFIELD · BITFIELD_RO
  • Writing bit N allocates (N>>3)+1 bytes: the string covers the highest offset ever touched.
  • Optimal for dense data; wasteful for sparse data.
redis-cli
127.0.0.1:6379> SETBIT b 7 1
(integer) 0
127.0.0.1:6379> TYPE b
string
127.0.0.1:6379> GET b
"\x01"   # it really is just bytes

03

Design decisions

The decisions that shaped the PR.

Design decisions

Goals & guardrails

  • Zero breaking changes. Every bitmap command returns the same values, errors, and edge-case semantics on both representations.
  • No new API to learn. The existing seven command families are the entire public surface.
  • Opt-in. Gated behind bitmap-default-roaring (default no); off means behavior mirrors upstream Redis exactly.
  • Same limits. Offsets stay bounded by proto-max-bulk-len × 8 bits: at defaults the highest valid offset is 2³² − 1, the historical string-bitmap limit.

🎯 Built for adoption

Zero breaking changes means workloads that stay on the bitmap commands adopt compression with a config flip and no code changes. It also gives redis-roaring module users a portability path into core, with one command surface everywhere.

Design decisions · the object model

A type, not an encoding

  • Original proposal: a transparent string encoding (like listpack → hashtable).
  • But encodings must be invisible, and a compressed bitmap cannot serve GET / APPEND / SETRANGE without materializing gigabytes.
  • Decision: a new bitmap object type. String commands return WRONGTYPE, the same behavior as every other non-string type.
"Define a 'real' bitmap data type instead of relying on String."LiorKogan

Design decisions · what changed

Other options we considered

🔀 A transparent string encodingconsidered

Invisible to users, like listpack → hashtable. But a compressed bitmap cannot serve GET / APPEND, and maintainers asked for a "real bitmap data type".

✅ A first-class bitmap typelanded

WRONGTYPE boundaries, its own RDB id and module API. The determinism rules follow from this.

📏 32-bit Roaring, hard 512 MB capconsidered

Simple, but no upgrade path for some redis-roaring users; and after the 64-bit ask, unbounded allocations became the concern.

✅ 64-bit internals, bounded surfacelanded

roaring64 inside; the exposed range stays at string parity (proto-max-bulk-len × 8).

"I'm ok with 32-bit only, at least as a first step."LiorKogan

Design decisions · conversion

How a key becomes Roaring

PathWhenNotes

🔒 Never implicit

With the config off, bitmap writes keep creating plain strings. Every path into the new representation can be enumerated from redis.conf.

↩️ No silent demotion

Roaring keys are never demoted back to strings. The type boundary is strict and one-way in v1.

Design decisions · determinism

The determinism problem

Nondeterminism is acceptable for invisible encoding decisions, never for WRONGTYPE-visible type decisions.

Design decisions · propagation

What actually crosses the wire

  • New internal command: BITCONVERT key, flagged INTERNAL; regular clients get unknown command.
  • Conversion and triggering write are wrapped in MULTI/EXEC and apply atomically.
  • SETBIT/BITFIELD: convert, then write. BITOP: write, then convert.
  • Replicas and AOF replay the stream verbatim; a replica with the config off still builds the Roaring key.
  • Writes to already-Roaring keys propagate as plain commands: zero overhead at steady state.

Design decisions · what changed

Other propagation designs we considered

1 · RESTORE … REPLACE KEEPMETADATA

Ship the converted value as a blob. Deterministic, but moticless: "KEEPMETADATA is very fine-tuned to this use case and may be fragile in the long run."

2 · internal BITCONVERT + BITOP_ROARING

Propagate the decision, not the bytes; in-place conversion preserves TTL & metadata implicitly. But it duplicated BITOP as a second command.

3 · BITOPMODE one-shot marker

oranagra: "better to add an optional argument to the command… rather than create an additional command with identical syntax." A stateful marker command, fragile in its own way.

4 · inline BITOP <op> ROARING dest

A review bot found the flaw: a destination key literally named ROARING becomes unaddressable. sundb: "no, it's not acceptable."

5 · BITOP + BITCONVERT in MULTI/EXEC ✓

Two plain commands: no new grammar, no parsing ambiguity, replayable anywhere. The simplest design of the five, and the one that held.

Design decisions · configuration

One boolean, zero heuristics

two modes, one meaningful value

Design decisions · persistence

Persistence: the portable format

  • Roaring keys persist as CRoaring's portable serialization: a cross-language spec, not a Redis-private blob.
  • Prefixed by the logical byte length. Roaring stores only set bits, so "string length" semantics (trailing zeros, ranges) must be carried alongside.
  • Dedicated RDB type id (RDB_TYPE_BITMAP) plus a version bump: old tools fail cleanly instead of misreading.
  • Same encoding everywhere: RDB, DUMP/RESTORE, full sync, AOF preamble.
  • trade-off RDB consumers can no longer treat bitmaps as byte arrays; the format is documented & versioned.
Design decisions · what changed

Other persistence formats we considered

💥 The blocker that turned it back

Saving raw bytes materializes the full logical range, and on replicated paths the "length ≤ proto-max" assumption does not hold. One set bit at offset 2⁴⁰ means ~128 GiB materialized at save time.

📐 The lesson

A compressed type must stay compact on every path: command replies, replication, RDB, DUMP. And a serialization format is a commitment to external tooling, not just to Redis.

Design decisions · bounded edges

Bounded worst cases

💣 BITOP NOT amplification

src/bitroar.h, the shipped bound
/* BITOP NOT fills every missing 2^16-bit Roaring
 * chunk in the logical range. Bound that allocation
 * amplification rather than the source's byte length:
 * dense sources above 512 MiB can remain cheap to
 * complement, while a sparse source cannot make one
 * command materialize an unbounded number of chunks. */
#define BITROAR_BITOP_NOT_MAX_MISSING_CHUNKS (1ULL << 16)

A flat 512 MB cap was rejected, since strings can legitimately hold that. The bound targets what NOT would have to create, and costs O(resident containers) to check.

🚪 Dense reads are debug-only

Dense materialization of a Roaring key is confined to a debug path (DEBUG BITMAP-RAW), and even that respects proto-max-bulk-len. A sparse bitmap cannot produce a huge reply through a normal command.

📏 64-bit capable, string-parity bounded

Internals are 64-bit (roaring64), but the exposed offset range stays exactly what string bitmaps allow. Raising the limit is a separate, deliberate decision.

Design decisions · scope

What v1 deliberately leaves out

Guiding rule: ship the smallest reviewable change that delivers the value. Every extra knob multiplies the review and test matrix.

Under the hood

A quick tour of the implementation.

Under the hood

Shape of the implementation

  • src/bitroar.c / bitroar.h owns the Roaring object: create, convert, read, write, serialize, defrag. ~3.1k hand-written lines; string paths in bitops.c stay byte-identical to upstream.
  • CRoaring 4.7.2 vendored (roaring64): 79% of the diff is the library, compiled with hidden symbol visibility.
  • Object header: encoding field 4 → 5 bits, refcount 23 → 22 bits. One bit traded for an unambiguous encoding namespace.
  • O(1) memory accounting per write via CRoaring's memory hooks, so MEMORY USAGE reports real live-heap data.
  • Expiry, eviction, keyspace, cluster, and defrag see a normal object.

Security & performance

Testing, fuzzing, the bugs found along the way, and benchmark results.

Security & performance · testing

Testing against the string implementation

The string implementation is the specification. The oracle suite runs every scenario in both modes; only TYPE may differ.

  • Differential fuzz: random strings loaded as both representations; all 8 BITOP ops compared on replies, dest bytes, and source immutability.
  • 206 bitmap test blocks across four suites (bitroar, bitroar-oracle, bitops, bitfield).
  • Infrastructure parity: replication-stream assertions, full-resync digests, corrupt dumps, defrag, cluster MIGRATE, keyspace events, AOF.
  • 93.8% line coverage on the core implementation file (Codecov, July 2026).
Security & performance · fuzzing

Fuzzing the deserialization paths

  • Threat model: hostile serialized payloads via RESTORE, RDB load, or the replication stream.
  • Validation is unconditional: exact-length framing, safe deserializer, CRoaring internal_validate, and highest-bit-fits-length, on every load, not just sanitize-dump-payload.
  • Corrupt-dump fuzzer: seeds 5 Roaring shapes and flips bytes inside the portable blob; the server must reject, never crash. Run with sanitize both on and off.
  • Module repo: 10 libFuzzer targets (ASan+UBSan); a manifest maps every command to a fuzzer, enforced in CI + daily cron.
  • Upstreaming the practice: a core fuzzing scaffold for Redis itself, proposed as its own PR.

Security & performance · findings

Bugs found during development

🐛 BITOP self-target use-after-free

A review-requested restructure moved operand cleanup after the keyspace store; BITOP AND k k on an empty Roaring key freed an operand still in use. Caught the same day; regression test added.

💥 Event-ordering segfault

Conversion once serialized the value after the notification path invalidated the pointer, calling createDumpPayload(NULL). Rule extracted: dump before you notify. Caught by the local test battery before any push.

🧟 Defrag pointer bugs

Bitset relocation computed an offset from freed storage; fixed offset-first, verified under ASan/UBSan. And CRoaring's ART node table leaves slot 0 uninitialized by design, so defrag walks are bounded to typecodes 1–5; otherwise the defrag allocator receives uninitialized pointers.

⬆️ Fixed upstream in CRoaring

Review of the vendored library found the non-atomic refcount decrement comparing the pointer instead of the value, so the last reference was never released. Fixed upstream in CRoaring #859 (Aug 2026). Redis itself was unaffected.

Wrapping up

Three things to remember

1

Same API, compressed engine

No new commands. Flip bitmap-default-roaring and a sparse key drops from 512 MiB to 313 bytes, measured.

2

Determinism is the design

Types are visible, so conversions are decided once and propagated explicitly as BITCONVERT, never re-derived on replicas.

3

Review made it better

17 tracked decisions, several reversed during review. Five replication designs before the final one. The result is simpler than the first draft.
